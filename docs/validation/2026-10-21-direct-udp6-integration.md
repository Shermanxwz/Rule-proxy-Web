# Opt-in direct UDP6 integration

This slice replaces the selected network workload; it does not append IPv6
attempts to TCP, IPv4 UDP or descendant experiments. Original Stage0 and legacy
paths retain their separate results. No proxy capability, firewall, route,
address, DNS or QEMU-network configuration change is part of this experiment.

## Binding and payload

The production actor targets only `fec0::2` and a host-owned high port. Its
fresh strict Agentic-only profile check precedes sockets. TEST_ONLY binaries
must fail production manifest admission and are never packaged.

The 17-member payload contains the existing base ten members, UDP6 executable
and manifest, the unchanged generic N0a ownership control/guest modules, and
UDP6 control/guest/flow modules. The packet decoder remains host-only. Exact
names/counts and equal-count forbidden substitutions are checked; no wildcard
deployment or artifact allowance is introduced.

UDP6 uses a dedicated nominal binding and source-checked canonical control
module. Guest-owned ordinary PID/report correlation and dedicated executor
audit correlation for the contained actor remain distinct. Actual inherited
wait/envelope, same-buffer report hashing and network-bundle production must
be exercised together in tests; fabricated normalized objects alone are not
evidence for that boundary.

## Work and reporting

The original Stage0 report remains first. The optional UDP6 path uses the
existing 120-second guest work clock and internal reserve, without resetting
the clock around executor startup. A fresh same-binary ordinary IPv6 echo to
the exact runner endpoint must succeed before sampler or contained launch.
Failure is inadmission, not isolation: no IPv4 fallback, guest-loopback
substitution, repeated attempt or network repair follows.

The existing sampler and three contained datagrams remain bounded; all ordinary
sample rows are retained. Separate versioned UDP6 result/private-body routes
keep their 4,096/65,536-byte limits. Result-first commitment and exact same-byte
body share one existing at-most-ten-second reporting allowance. Missing private
upload cannot erase a valid independently bound API/echo observation.

## Capture and qualification

The existing bounded capture owner, startup-before-link ordering, full QEMU
lifetime capture, 64 MiB retained cap, payload admission and 65 MiB reserve are
reused—not the IPv4 decoder or TCP denial qualifier. Receiver and capture stay
owned until the observed producer exit. Parsing precedes work deletion and
final absence qualification follows confirmed cleanup.

A complete four-report bundle is required for the packet manifest. Missing a
whole report means packet unavailable, never zero observed packets. Independently
bound selected API/echo facts and receiver observations remain available. With
a valid complete bundle, typed failed ordinary controls or later cleanup
failure cannot erase an already decoded payload observation; they forbid an
absence conclusion. Pure parsers do not authenticate the provenance of inputs.

## QEMU and libslirp provenance

Before intentional NIC enable, the exact held QEMU process is correlated with
its start time/executable and bounded maps. Normal mapping segments may share
one library backing identity; missing, static, deleted, ambiguous, replaced or
unreadable evidence fails admission. A no-final-symlink regular-file descriptor
is matched to mapping device/inode, hashed and bracketed by stable metadata,
mapping and process observations. Owned descriptors have one-shot closure and
uncertainty affects cleanup. No `map_files`, `ldd`, memory access, library
execution or privilege escalation is introduced. The provenance helper performs
no package installation or download.

Package owner/architecture/version and local installed-file integrity agreement
are reported separately. These identify a mapped backing file and local
metadata agreement—not resident pages, trusted host-root resistance, upstream
source equivalence or networking semantics. Actual same-API ordinary guest
IPv6 echo remains the behavioral admission. Source feasibility and hosted
`::1` mechanics cannot replace that observation.

The short job provisions the same official Ubuntu QEMU package for its tiny
paused owned-QEMU provenance gate, without a Windows guest. It proves only its bounded ownership,
mapping/file checks and cleanup; it is not guest-alias or isolation evidence.
All reads, subprocess waits and cleanup use existing deadlines and byte caps;
bounded caller waits do not promise arbitrary OS calls complete on time.

## Review boundary

No additional runtime is authorized by this diagnostic. Required checks include exact canonical imports,

uncertainty, exact 17-member ZIP and legacy parity. Neither hosted mechanism
success nor a short integration gate authorizes a Windows runtime by itself.

## Version 2 receive context (code-only candidate)

Site-local scope is not universally zero and a site Zone is not an interface index. The new versioned contract retains the fixed endpoint, wildcard bind, sendto arguments, attempt count and original deadlines. It enables the socket-local IPV6_PKTINFO option, obtains the provider's WSARecvMsg extension pointer, and replaces the receive call with one synchronous WSARecvMsg under the existing nonblocking/select deadline. No extra sends, routes, addresses, firewall rules, capabilities or QEMU networking settings are introduced.

One aligned ancillary buffer must contain exactly one bounded IPV6_PKTINFO record with the expected header length/level/type and no truncation or other flags. Its ingress interface index is compared with independently queried pre/post route and interface context. Fixed-size GetBestInterfaceEx, GetIpInterfaceEntry and GetIfEntry2 observations must agree on stable index/LUID/site Zone and an operational, connected nonloopback interface whose six-byte MAC matches the existing fixed VM_NIC_MAC/e1000 configuration. The expected MAC is not derived from the observed interface. These synchronous kernel calls consume the existing budget; no hard OS-call completion guarantee is claimed.

The installed SDK scope helper normalizes only accepted Level 0 or Site encodings, after which the full normalized value must equal the independently derived expected site Zone. Requiring a nonzero expected Zone is a conservative fixture admission, not a universal statement that zero is invalid under Windows. The packet-info address is the local destination, not the remote peer: its class is sanity-checked, not independently verified against an address-ownership table. Actual arrival evidence comes from packet-info interface index plus the independently bound NIC context. TEST_ONLY loopback code requires the real loopback interface and exact ::1 local destination; it cannot establish the production QEMU/site-zone contract.

Each attempt carries a compact versioned context array with fixed observed/passed masks; unknown bits and passed-but-unobserved predicates are rejected. Missing or failed context cannot qualify an echo. The existing zero-scope Boolean remains an observation, not a required true predicate. Complete 40-row native, private-bundle and public-envelope representations must remain within 32,768, 65,536 and 4,096 bytes respectively.

selected_nonce_payload_observed denotes only a fresh, strictly actor/report-bound native receive observation of the complete expected nonce bytes after successful nontruncated reception. It is not peer identity, delivery-source authentication, outbound egress or a qualified echo. It survives a wrong peer or later context/cleanup failure. selected_echo_observed requires the full peer context; ordinary admission remains strict. Host packet.selected_payload_observed is a separate capture fact. Public output excludes raw interface indices, LUIDs, MACs, zones, addresses and ports.

Required regressions cover ancillary bounds/duplicates/truncation, SDK scope normalization, wrong level/zone/interface, scope-zero false with valid full context, payload positives despite later failure, and error/partial/stale/unbound negatives. Hosted owned-loopback mechanics and synthetic helper tests precede any separately authorized guest attempt. No runtime is authorized by this candidate.

## Capture failure diagnostics (code-only follow-up)

The third guest run admitted the production ordinary receive-context contract and
42 ordinary echoes; three selected sends were locally accepted, with no selected
receiver observation. Its capture was **incomplete**, with overflow, opaque
protocol and truncation reasons. Zero selected decoded matches therefore did not
establish bounded packet absence. Deleted raw capture/body data cannot identify
the original offending next-header or truncation branch retrospectively.

A separately reviewed cleanup correction preserves every capture error and the
complete-capture predicate while limiting failed-path drain grace to two seconds
inside the original absolute cutoff. Normal drain allowance is unchanged. Its
Linux owned-process and paused-QEMU short gate passed; this repairs a reproducible
failure-finalization delay, not overflow or packet-decoder acceptance.

The prior version 1 diagnostic-only projection internally counts the existing opaque next-header
branch by fixed 0..255 protocol enum. Public detail lists at most 16 positive
[protocol, count] pairs in enum order, with explicit omitted-category and
omitted-event totals and a detail-completeness flag. Listed plus omitted totals
exactly account for the internal counts; truncated detail is never an absence
claim. It also distinguishes partial record header, captured/original length
mismatch, and partial record body. Counters can overlap:
a length mismatch may precede a partial-body failure before that record is counted
as consumed. Unknown/unattempted decoding remains unavailable, not observed zero.
No unsupported protocol or truncated capture is newly admitted. Selected payload
observations remain sticky under later failure; diagnostics never qualify absence.

A separate fixed projection of already available capture facts reports the
retention limit, retained/drained byte counts, overflow and finalization/exit/
closure Booleans. It contains no packet bytes, nonce, identity, address, port,
path or free-form exception. The 64 MiB retention cap is a byte-prefix bound, not
a record-alignment guarantee or a disk-exhaustion assertion.

Native reports remain capped at 32,768 bytes, private flow bodies at 65,536 bytes,
and the **guest result envelope** at 4,096 bytes. These are not a claim that the
entire host public artifact fits 4,096 bytes: that artifact also contains receiver,
provenance and packet evidence. The added host packet projection has a separate
4,096-byte worst-case serialization check; complete host-artifact serialization
is measured without dropping existing result fields or inventing a previous
whole-artifact byte cap. No guest/native protocol, network call, acceptance rule,
capture resource bound, or runtime permission changes in this diagnostic slice.

The settled conservative independent-field ceiling measures 3,855 bytes for the
host-nested packet projection with indentation and newline, and 9,165 bytes for
the full host artifact with indentation and newline. These maxima need not occur
jointly in a valid report; the latter is a measurement, not a newly invented
runtime writer cap. Dense public 256-entry counts failed the pretty-print bound
and were replaced by the explicitly incomplete sparse detail above, not by an
increase to any existing limit.


## ICMPv6 diagnostic version 2 (code-only candidate)

Runtime04 remains immutable and inconclusive. Its two opaque Next Header 58
observations were on the existing guest-source-MAC / destination-fec0::2 path.
They do not identify benign traffic or an error cause. Deleted private capture
cannot be reconstructed by this change. No rerun is authorized here.

Version 2 changes only diagnostic detail. The internal 256-entry next-header
counts remain complete; public detail now retains the first two nonzero protocol
numbers in sorted enum order, with exact omitted-category and omitted-event
totals. ICMP type/code detail keeps the first four distinct pairs encountered,
then sorts those tracked pairs for serialization. Later events for tracked pairs
still increment them; untracked events increment an explicit omitted-event count.
No omitted distinct-pair count is invented. Each detail-complete flag concerns
only its diagnostic listing, not capture completeness or absence.

The fixed arrays are:

- `checksum_counts[3]`: outer ICMPv6 checksum valid, invalid, uncheckable.
- `quote_counts[4]`: complete classic IPv6-plus-UDP quote, partial quote,
  malformed quote, unsupported/not-error.
- `quote_detail_counts[14]`: inner UDP checksum valid/invalid/uncheckable (3),
  exact selected/ordinary/other payload (3), request-bound/reply-bound/unbound/
  ambiguous tuple (4), outer-error address relation match/mismatch (2), and
  joint checksum-consistent bound selected/ordinary quote observations (2).
- `raw_selected_nonce_match[2]`: Boolean and distinct selected-case count 0–3;
  the Boolean equals whether the count is nonzero.

The first four quote-detail groups independently partition complete quotes. The
last two are per-event conjunctions, not an inference formed by combining
marginal counters from different packets. Binding requires exact known payload,
fixture and ephemeral ports, the quoted guest address equal to the outer guest
source, and no source-port collision. An unspecified, multicast, loopback, IPv4-mapped or
fixture-equal outer source, or an ephemeral port equal to the fixture port, is
conservatively tuple-ambiguous for this diagnostic—not universally invalid UDP.
Raw and exact-payload observations remain available. The error-address relationship separately
compares outer destination with quoted source. These are syntax/consistency
observations, never authentication of the quoted sender, original delivery,
actor attribution, or proof of no selected IPv6 egress.

Raw selected-frame bytes are searched first within bounded captured ICMP bytes,
independently of checksum, quote syntax, direction or later cleanup. This new raw
observation is not the existing direct-UDP selected-payload flag. Forged bytes in
junk may establish only raw observation; even a fully checksum-consistent forged
quote remains unauthenticated. Failure or omitted diagnostic detail cannot erase
existing direct-UDP, receiver or native-send observations.

Only the existing reached-NH58 path is examined. Outer extension headers or an
unavailable fixed eight-byte error header make quote interpretation unsupported;
an outer message shorter than four bytes or with extensions has an uncheckable
checksum. Types 1–4, with any code, are framing-only candidates, not assertions
about registered code meaning. A legitimate short invoking-packet prefix is
partial, not malformed and not a negative match. Visible impossible version or
length is malformed. Nonzero RFC4884 length in type 1/3 byte 4, jumbo lengths,
quoted non-UDP next headers, and surplus quotation tails remain unsupported.
There is no recursion, extension traversal in quotations, reassembly or protocol
fallback. Outer and inner checksum observations remain separate; the existing
core `checksums_validated=false` and every absence predicate remain unchanged.

The conservative independent-field serialization composition retains every old
core field and measures **4,015 bytes** for the actual host-nested packet with
indentation and newline, below 4,096. The corresponding full host artifact is
**9,325 bytes**, a measurement without a new whole-artifact cap. A separate
self-consistent counter witness measures 3,971 nested bytes; it is not claimed
maximal or an observed packet trace. Native, guest-envelope, private-body,
capture-size, process and time limits are unchanged. No network, actor, guest,
policy, lifecycle or runtime activation change accompanies this candidate.

## Strict fixture-scoped ND admission (code-only candidate)

The inner packet result is now **schema version 2**, independently of the optional
version 3 diagnostic. Thus a missing or malformed diagnostic (`null`) cannot hide
which parser admission contract ran. Historical archives and their inconclusive
results are unchanged; this candidate does not reclassify deleted captures.

Only a narrow, explicitly specified neighbor-discovery profile may stop adding
an opaque-protocol reason for that individual packet. Other opaque packets still
add their reasons, including in mixed captures. Ordinary controls, complete
capture, fresh report bindings and cleanup remain necessary for the existing
bounded **direct selected UDP datagram** absence claim. This does not establish
absence of selected bytes elsewhere, absence of IPv6 egress, ND authenticity,
address ownership, or a causal response to any particular send.

The parser makes two sequential bounded passes over the same immutable PCAP
bytes. The first retains at most 42 ordinary row keys and one usable observed
communication source `G`. Exact ordinary nonce/phase/index/port/destination/MAC
observations must have a nonzero, valid UDP checksum. Every required ordinary row
must be represented with `send_invoked` and `nonce_verified`, preserving the
existing final-after first-witness ordering. A bad-checksum duplicate, conflicting source, unusable source,
port collision or incomplete capture taints the ND witness. Relevant fixed-destination
guest frames with base next-header values 0, 43, 60, 51, 44 or 50 also taint
that witness through the outer-layout bit: the bounded first pass cannot exclude
an ordinary duplicate behind an unsupported layout. This is not a claim that
the frame is malformed, and no extension parser is added. `G` correlates
observed ordinary communication; it is not an operating-system address-ownership
assertion. Existing direct-UDP parsing and its global `checksums_validated=false`
field are not upgraded by this stricter ND-only checksum witness.

The second pass admits only the existing guest-MAC-to-`fec0::2` path with direct
Next Header 58, complete exact IPv6 framing, hop limit 255, code zero and a valid
ICMPv6 checksum. There are no extension headers, fragments or jumbograms. NS must
have source `G`, target `fec0::2` and zero reserved bits. NA must have source and
target `G`, R=0, S=1, either O value and zero remaining reserved bits. The exact
ICMP body is either 24 bytes without options or 32 bytes containing one eight-byte
link-layer option: type 1 for NS or type 2 for NA, length 1, with the existing VM
MAC. Other legal variants or unknown options are unsupported by this fixture
profile, not universally invalid ND. A definite wire/RFC rejection takes priority;
otherwise unsupported, unbound, raw-byte or witness failures prevent admission.

Complete selected-frame patterns and the shared ASCII case nonce are observed
across bounded candidate bytes before qualification. Those observations survive
later failures and prevent the ND exception. The shared case nonce is used by
ordinary traffic too: seeing it does not attribute a packet to the selected actor.
Raw direct-UDP, receiver and native-send facts remain independent and sticky.

Diagnostic v3 preserves all v2 fields, retains two next-header detail rows and
reduces displayed ICMP type/code pairs from four to two, with unchanged explicit
omitted-event accounting. Historical opaque-next-header counts include candidates
that the new ND profile admits; diagnostic counts are not an opaque verdict.
Its fixed `ndp[10]` vector records profile-NS, profile-NA, rejected, unsupported,
failure-bit mask, exact ordinary witnesses, checksum-valid witnesses,
checksum-invalid witnesses, source state and shared-case-nonce Boolean. The first
four counts partition NS/NA candidates, and valid plus invalid equals exact
ordinary witness count. Counts include duplicate records and are bounded by the
record limit, rather than by the 42 retained row keys. Source state is 0 for no
usable source, 1 for exactly one usable source, or 2 for two or more usable sources
(sticky conflict); unusable addresses have a separate failure bit. Source
observations include invalid-checksum duplicates, so state 1 alone does not
qualify the witness. The 19-bit mask has only these fixed meanings, in order:
outer layout, length, hop limit, code, checksum, RFC address constraint, fixture
address constraint, flags/reserved bits, option framing, option shape, option MAC,
complete selected bytes, ASCII case nonce, missing witness, bad-checksum witness,
source conflict, unusable source, binding collision and capture framing.

The unchanged conservative independent-field composition measures **4,060 bytes**
for the nested packet result with indentation and newline, below 4,096; the full
host artifact measures **9,370 bytes**, without a whole-artifact cap claim. No old
core result field is dropped. The two-pass design adds fixed bounded state, not a
second full-capture copy. Existing capture-reader transient copies remain; the
65 MiB admission reserve is a **disk** planning allowance, not a RAM ceiling.
Native/guest/private-body bounds, capture cap, deadlines, process lifecycle,
network calls, policy and runtime activation are unchanged. No VM run or
publication is authorized by this code-only candidate.

## NA address-relation presence (diagnostic version 4, code-only candidate)

The inner packet schema remains 2 and all strict ND admission predicates,
including the fixture-address failure bit (bit 6, value 64), opaque reasons and
bounded direct-UDP absence formula are unchanged. Diagnostic version 4 merely
extends `ndp` from ten to twelve slots; no earlier field is removed or redefined.
Historical archives are not reinterpreted by the new detail.

For an already reached type-136 NA candidate, an address relation is known only
when at least the fixed 24-byte body is available and the complete ordinary
witness is ready. Any calibration failure—including missing rows or flags,
terminal ordering, checksum, unsupported layout, binding collision, framing,
unusable source or source conflict—makes this relation unknown. A unique-looking
source state alone is not enough. Unknown candidates increment `ndp[11]`, an
unknown-NA event count, without inventing an address result.

For known relations, define S as outer source equals observed ordinary source G,
T as NA target equals G, E as outer source equals NA target, and D as outer
destination equals the fixed fixture. D is already true on the unchanged parser
path. Joint values `S | (T<<1) | (E<<2) | (D<<3)` of 8, 9, 10, 12 and 15 map,
in that order, to the five bits of `ndp[10]` (range 0–31). This is a set of joint
patterns actually seen, not per-pattern frequencies or independent marginal
Booleans that may be combined across packets. Known address-byte relationships
are retained even if that NA later fails checksum, code or flags. They do not
establish authenticity, OS address ownership or a cause for the observed traffic.
The new slots never influence ND admission or any stronger egress claim.
Producer-side projection checks use a private bounded NA-event count, including
short bodies, to reject impossible unknown counts or pattern cardinalities. This
count is not exported and cannot be reconstructed from truncated type/code
detail; repeated occurrences of one known pattern still set only one bit.

The real conservative independent-field composition, retaining every previous
maximum field, measures **4,092 bytes** for the host-nested packet projection with
indentation and newline, within the unchanged 4,096-byte limit. Its full-host
serialization measures **9,402 bytes**, not a runtime writer cap. These maxima
need not coexist in a valid trace; separately validated projector fixtures check
self-consistent known, mixed and unknown observations. No capture, guest, native,
policy, lifecycle, frequency, network or runtime change is introduced here.

## Independent endpoint-payload absence and captured markers (code-only candidate)

This is a new contract, not a reinterpretation of any historical archive. The
outer host packet projection is schema 2 and its inner packet result is schema
3, both scoped `runner_ipv6_outer_udp_endpoint`. The former
`bounded_no_selected_udp_datagram` field and corresponding status are replaced by
`bounded_no_selected_outer_udp_payload`. Older scope/schema pairs are rejected
rather than relabelled. Native, guest and private-flow wire formats are unchanged.

**A — exact outer UDP payloads at the fixed endpoint.** The Boolean refers only
to the three complete expected contained payloads in outer IPv6 UDP datagrams
with the guest source MAC, fixed `fec0::2` destination and fixed destination port.
It is not absence of every UDP datagram, selected bytes in other protocols,
selected activity, or IPv6 egress. Complete supported IPv6 framing that ends in
Next Header 58 is definitely non-UDP for A, regardless of ICMP semantics, ND
profile or inferred address G. Malformed IPv6 chains, fragments, ESP and capture
truncation remain inconclusive; the ordinary controls, binding and capture/cleanup
requirements are not removed. ND/G measurements continue as diagnostics only and
cannot admit an otherwise ambiguous UDP path.

**B — durable bounded record-byte observations.** A separate core `marker_scan`
is `null` when unattempted or when trusted patterns cannot be derived from a valid
manifest. Otherwise it is `[scan_complete, selected_frame_mask, shared_case_seen]`.
The three mask bits correspond to the three full expected selected patterns;
the shared ASCII case nonce is also used by ordinary traffic and is not selected
actor attribution. The scan examines bounded records with the exact guest source
MAC before EtherType, destination, protocol and port filtering. Matches are
contiguous within one record, with no cross-record reassembly. A safely delimited
partial body may retain positive observations from its available prefix if the
MAC is extractable, while the scan remains incomplete; an invalid record header
cannot supply an invented frame boundary. These markers are core evidence and
remain present if optional diagnostic projection fails.

A may be true while B observes selected bytes in ICMP or another record. In that
case the positive status `selected_record_bytes_observed` takes precedence, while
the independent A Boolean remains visible. Late host prerequisite or cleanup
failure revokes A but does not erase markers, direct selected-payload observations
or their positive status. `scan_complete` concerns exhaustive record-byte coverage
of the supplied bounded PCAP, not experimental-window or lifecycle completeness.
It may remain true for a fully scanned retained file whose capture lifecycle is
incomplete; a negative experimental claim would require both kinds of coverage.
No overall isolation pass, authenticated sender claim
or absence of IPv6 egress follows from either result.

Diagnostic version 5 reduces displayed next-header and ICMP type/code detail to
one row each; internal counters and exact omitted-event/category accounting are
retained. All earlier diagnostic vectors remain, including the ICMP-local raw
marker detail, distinct from B's broader scan. The conservative full-field upper
composition measures **4,054 bytes** for the actual host-nested packet projection
with indentation and newline and **9,364 bytes** for the full host artifact. The
latter remains a measurement, not a new writer cap; the positive-status variant measures 4,040 bytes and is
also checked against the unchanged 4,096-byte packet limit. Same-byte bounded
scans add no full-capture copy, and existing transient-reader allocations remain.
No network, policy, capability, native/guest operation, process lifecycle, resource
limit or runtime activation is changed by this candidate.
