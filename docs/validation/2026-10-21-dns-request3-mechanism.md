# DNS REQUEST3: hosted mechanism gate, not isolation proof

## Scope and current evidence

This is a separate **TEST_ONLY** mechanism experiment. It asks whether the installed official Windows SDK and hosted Windows DNS API can submit a bounded request through `DNS_QUERY_REQUEST3` to an owned IPv4 loopback responder on an ephemeral high port, and whether the caller and responder agree on a fresh synthetic query and answer.

The first compiled Windows API attempt returned status 87, with zero owned-responder queries observed, an empty effective NRPT rule set, and confirmed owned cleanup. This is a failed mechanism attempt, not DNS denial or isolation evidence. Source review and pure parser tests are not a substitute for a successful actual Windows exchange. A later successful gate establishes only the tested hosted API/responder mechanism. It does **not** establish ordinary non-administrator execution, BaseContainer/AppContainer enforcement, guest access to `10.0.2.2`, DNS blocking, packet egress suppression, or Linux-equivalent isolation.

The first actual Windows gate stopped at C++ compilation: the installed SDK did not expose `DNS_CUSTOM_SERVER::ServerAddr` under the original header set. The SDK header guards this named union member with `_WS2TCPIP_H_`. The corresponding pinned Microsoft sources are the [DNS custom-server union guard](https://github.com/microsoft/win32metadata/blob/2f767671802301cf043c717d66bf004ed7863487/generation/WinSDK/RecompiledIdlHeaders/shared/windnsdef.h#L1561-L1567) and [WS2tcpip header guard](https://github.com/microsoft/win32metadata/blob/2f767671802301cf043c717d66bf004ed7863487/generation/WinSDK/RecompiledIdlHeaders/um/WS2tcpip.h#L17-L41). The compatibility candidate adds the official `ws2tcpip.h` include before `windns.h` and records that fourth SDK header alongside the existing provenance checks. It does not replace the SDK structure, cast into undocumented storage, change query options, or establish an API result. `DnsQueryEx` and the owned-responder mechanism were **not run** in that failed attempt.

The subsequent Windows differential tested one narrow synchronous-call hypothesis: the existing non-null cancellation pointer versus a null cancellation pointer. Both cases retain the same official version-3 request, query options and owned high-port mechanism; neither substitutes a default resolver or changes an OS setting. Both use the same owned responder, nonce and port, with a fresh child and native context for each case. The null-pointer case starts only after an observed non-pending baseline report, exit code 0 and confirmed owned-child cleanup. Each wait is at most 15 seconds and clipped to the same overall deadline minus the existing cleanup reserve; pending, timeout or uncertain exit stops the pair. Locked receiver snapshots before and after each case yield temporal count differences, not proof of DNS-broker identity or independent attribution of a delayed shared-nonce request. Both run within the same existing 60-second overall budget. Both cases returned 87 with no owned-responder queries, so this differential did not resolve the failure and does not authorize another fallback. The earlier compile failure and this later API failure remain separate observations.

Existing production IdentityOnly and N0a actors, policies, VM payloads, proof predicates, reports, and runtime workflows remain unchanged. No result from this gate changes the prior strict Stage0 failure or any existing acceptance result.

The separate `--run-no-query-diagnostics` mode does not run either API case. This is provenance-only diagnostic evidence: it does not identify the cause of status 87, prove ABI compatibility, or establish mechanism or isolation success. No resolver request or owned DNS responder is started in this mode. Unknown or failed diagnostic observations remain explicit rather than triggering another query mode. The existing 5/8-minute job budgets, TEST_ONLY separation and no-artifact boundary are unchanged.

The mechanism sections below do not describe work performed by the no-query mode.

## Prior explicit-port differential candidate

The `--run-port-pair` candidate compares an owned ephemeral high port versus an explicitly supplied port 53. The same synthetic nonce, request options and non-null cancellation pointer are used, with fresh caller processes/contexts. This tests only the explicit-port hypothesis; it does not select a default resolver, alter DNS settings, or imply ordinary-user or isolation acceptance.

Before either API call, the candidate must establish that all UDP port-53 endpoints are absent, exclusively bind its owned `127.0.0.1:53` responder, and privately verify that the only resulting port-53 endpoint is that exact address and owned process. Busy or unknown inventory, bind failure or ambiguous ownership means no API attempt. Raw endpoint/PID inventory is not published. Per-case waits remain at most 15 seconds inside the single existing 60-second deadline; baseline pending, timeout or uncertain completion/exit prevents the second call. Both receiver sockets are owned before either case starts, and both receivers are observed before and after each case. Unexpected activity at the other receiver prevents a positive mechanism result; `pair_complete` requires both cases to have observed completion and confirmed cleanup. Each receiver has a 32-datagram handling quota and bounded reads. Receiver observations do not prove independent DNS-broker identity.

Both case results must be retained. If both return 87, the port differential has not resolved the failure and closes this hypothesis without fallback or another unreviewed query variant. This candidate requires its own reviewed actual gate result; pure tests do not establish API eligibility or successful DNS exchange. The exact marker, 5/8-minute job bounds and no-artifact/no-VM limits are unchanged.

## Separate read-only port-preflight diagnostic

The attempted explicit-port pair stopped at preflight admission, before any DNS API call. The previous result does not distinguish occupied port 53 from an inventory error; neither cause is assumed. No API denial or port-hypothesis result was established.

The `--run-port-preflight-only` mode is read-only. It executes the existing unfiltered `Get-NetUDPEndpoint` enumeration, filters port 53 and caps observations at two. Only closed empty/present/enumeration-error/parse-unknown/unobserved status, a count class of 0/1/2-or-more or null, and bounded wait, parse, exit and owned-cleanup facts may be published. The single PowerShell child wait is at most 5 seconds inside the unchanged 60-second overall budget. Enumeration errors additionally expose only the fixed exception-family labels `CimException`, `CimJobException`, `CommandNotFoundException`, `UnauthorizedAccessException` or `other`; success uses null and unknown families use `other`. This family observation does not identify the underlying CIM cause; no category, raw message or fully qualified error identifier is emitted. It does not select a different filtering API based on an unproven cause. There is no native-actor execution, NRPT query, responder, bind, DNS request, setting change or automatic port-pair retry. The retained compile step is source/build validation only. Existing job budgets and the no-artifact boundary remain unchanged. A successful read-only diagnostic describes inventory visibility, not DNS eligibility or isolation.

## Fixed alternate-loopback conditional pair candidate

The workflow selects only `--run-loopback2-port-pair` (versioned result `loopback2_port_pair_v1`). This code-only candidate uses the single fixed address `127.0.0.2`, never an address search, to compare an owned high port with explicitly supplied port 53. Both cases retain the same query name, request options and non-null cancellation pointer, using fresh native contexts. There is no default-resolver fallback, service change, address configuration or global DNS modification. The candidate is not an ordinary-user or isolation acceptance test.

Admission requires a complete bounded private UDP port-53 inventory of at most 64 records and 4096 bytes; a 65th record causes refusal rather than truncation. Wildcard endpoints, every IPv6 endpoint, the target address, unknown records, failed enumeration or truncation reject admission before either query. Only after admission may the candidate exclusively bind its owned target socket. Private before-bind, post-bind and after-close inventories must preserve unrelated baseline endpoints and identify only the intended owned change; raw addresses and process identities are not published. These are snapshots, not continuous service-liveness proof, and do not authorize touching any pre-existing endpoint.

Both receiver sockets must be owned before the pair starts. All query waits remain at most 15 seconds under one unchanged 60-second budget, with no second case after uncertain baseline completion or cleanup. Both case outcomes and cleanup remain explicit; query failures do not trigger another address or mode. Existing TEST_ONLY separation, 5/8-minute job bounds, no-artifact and no-VM limits remain unchanged. This section describes a code-only candidate requiring final review, not an observed exchange or authorization to run it.

## Isolation from production and external services

- The new binary is compile-time TEST_ONLY, with a distinct name/build directory and non-deployable manifest. It is not a production actor or a guest payload member.
- Retained original modes use the fixed loopback address `127.0.0.1`; the selected alternate pair uses only fixed `127.0.0.2`, with an owned ephemeral high port and conditionally admitted explicit port 53. All responder sockets bind an explicit loopback address, never a wildcard. They answer only bounded synthetic requests under test and perform no forwarding or proxying.
- No VM, extra account, global DNS setting, NRPT rule, firewall rule, hosts entry, public resolver, or user device is changed or used.
- No fallback to an existing resolver implementation is allowed after unsupported SDK/API/transport behavior. Unsupported, unobserved, timed-out, malformed, or mismatched results are failed/inconclusive mechanism evidence, not isolation success.
- The dedicated `[dns-request3-gates]` marker is limited to the exact experimental branch and push event. The Linux job is bounded to 5 minutes and Windows to 8 minutes. Neither uploads artifacts or starts a VM. A DNS-only marker must not admit any existing direct, capture, or serviced native job.
- Mechanism controller/native result output is restricted to closed result fields. Compiler diagnostics and build-source paths are separate build evidence, not private query observations. Raw queries, nonces, socket tuples, native report bytes, and exception text are private fixture inputs, not published evidence.

## API contract and limits

Microsoft documents `DNS_QUERY_REQUEST3` as a version-3 request accepted by `DnsQueryEx`, with an explicit custom-server array. The custom-server list and the older DNS-address list must not both be populated. The custom-server route bypasses system-configured DNS servers, **except that a matching NRPT rule takes precedence**. Therefore an exact owned-responder observation is required; merely populating the structure does not prove which resolver handled a request. The fixture does not edit NRPT; its preflight is a read-only check that the effective rule set is empty, refusing the mechanism attempt if that cannot be established. [DNS_QUERY_REQUEST3](https://learn.microsoft.com/en-us/windows/win32/api/windns/ns-windns-dns_query_request3)

The custom-server structure exposes a socket-address representation and distinguishes ordinary DNS from DNS-over-HTTPS. The implementation must use official SDK definitions, not a guessed ABI or a handwritten replacement layout. Documentation requires the socket-address header before the DNS header when using `ServerAddr`. These are mechanism prerequisites, not proof that a particular high-port request succeeds on the tested system. [DNS_CUSTOM_SERVER](https://learn.microsoft.com/en-us/windows/win32/api/windnsdef/ns-windnsdef-dns_custom_server)

`DnsQueryEx` supports synchronous and asynchronous operation. This fixture selects the synchronous form with a null completion callback. It validates a completed status and exact answer before releasing returned records. If the API unexpectedly reports pending, the fixture retains the request, result, query name, custom server and cancellation storage without unwinding, and waits for the parent to terminate the exact owned child. The separate injected-pending case tests that lifetime/teardown path without making a DNS call. [DnsQueryEx](https://learn.microsoft.com/en-us/windows/win32/api/windns/nf-windns-dnsqueryex)

Cancellation is not a completion barrier. The current synchronous fixture does **not** call `DnsCancelQuery`; the documentation matters as a constraint against substituting cancellation for confirmed completion in a future design. Its unexpected-pending path instead retains storage until exact owned-process teardown. That teardown does not prove independent completion of any DNS broker operation. [DnsCancelQuery](https://learn.microsoft.com/en-us/windows/win32/api/windns/nf-windns-dnscancelquery)

The request uses wire-only, cache-bypass, no-hosts, no-NetBT, no-multicast and fully-qualified-name options. It does not request acceptance of a truncated response. Neither the custom UDP server type nor these options are presented as proof that TCP fallback is impossible; the tested responder returns a complete, non-truncated answer. The mechanism gate does not claim a complete packet trace. [DNS query options](https://learn.microsoft.com/en-us/windows/win32/dns/dns-constants#dns-query-options)

## Required gate evidence

The mechanism controller uses one 60-second absolute deadline for caller waits across preflight, cases and owned cleanup; a later case cannot renew it. Per-child waits are clipped to that remaining budget. This is not a claim that every process-start/API/cleanup call is hard nonblocking, or that a DNS broker operation is cancelled; the outer CI step/job bounds remain separate. The Windows result must identify the exact compiled SDK/API mechanism and distinguish native-call success from owned-responder observation. A valid mechanism exchange requires the fresh expected question, response identity and answer to match, together with finite responder handling and observed owned-process/thread/socket cleanup. Negative parser fixtures must reject malformed, unrelated and truncated messages rather than counting silence as denial.

The publication gate also tests exact marker truth tables, TEST_ONLY exclusion from production payload/artifact paths, and zero-test/skip refusal. Any later guest or contained DNS experiment needs its own reviewed integration, same-process identity/provenance, ordinary positive controls, transport evidence and failure classification. This document grants no such runtime clearance.
